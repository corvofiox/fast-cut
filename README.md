# Fast Cut

**给录制视频做粗剪的 Windows 工具。轻、快、不掉画质。**

录完一段视频（录屏、直播回放、网课、会议记录），你多半只需要做一件事：**把不要的段落删掉**。
Fast Cut 就是为这一件事做的——导进来，删掉废段，导出，画质尽量一帧不动。

**两种导出模式**（导出面板里一个勾选框切换）：

- **吸附关键帧**（默认）：切点前移到最近的关键帧，**整段流拷贝**——零重编码、零画质损失、最快。
  代价是切点会多带一小段开头（预估里写明带多少）；切点对准 GOP 边界就是纯拷贝。
- **精确模式**：切点逐帧精确、绝不吸附；入点那一小段有损重编码（CRF 18、同 profile），其余仍流拷贝。

两种模式共用同一套防吞保护：吸附回溯**绝不越过上一个切点**——间隙比 GOP 短时该段自动改为
局部精确，你删掉的素材永远不会回到产物里。

---

## 1. 这是一个什么项目

一个**只做粗剪**的桌面视频工具。它不试图成为剪辑软件，只把"删掉不要的段落"这一件事做快、做准、
做得不掉画质。

**它做的事：**

- 导入一个视频文件，立刻能播放预览；
- 像普通剪辑软件一样切分、删除、调整切点、改变片段顺序；
- 导出成一个文件（或每段一个文件），**能流拷贝的部分一律不重新编码**。

**它不做的事**（明确划出，避免变成另一个剪映）：

- 时间线多轨、转场、滤镜、调色、字幕烧录、变速、加水印；
- 导出到与源**不同的编码**（那是格式转换，是另一个产品）；
- 网络视频下载、录屏、压缩率优化、工程文件保存。

技术上是一个 Electron 桌面应用（Windows 10/11），**零运行时依赖**，内核是一层不依赖 Electron
的纯 Node 模块，所有实际编解码都交给内置的 ffmpeg。自写代码约 6200 行，代码包（app.asar）
只有 0.26 MiB。

## 2. 为什么要有这个项目

**因为录制视频的粗剪，现在被两件事拖累：慢，和掉画质。**

**第一，录制素材天生又长又"废"。** 一次录屏动辄半小时到几小时，里面真正要留的可能只有几分钟。
你的需求不是"精修"，而是**快速把废段切掉**。可通用剪辑软件为了通用性背了太多东西——项目文件、
代理媒体、后台转码、复杂时间线——启动要等、导入要等、导出还要等。你只是想删几段而已。

**第二，也是更要命的：一旦重编码，画质就回不来了。** 视频压缩是有损的，每重编码一次就再损一次。
你辛苦录的 4K/1080p 素材，如果为了剪掉中间一段而被整体转码一遍，**画质白降一档**——而且不可逆。
通用工具里"精确剪辑"往往意味着"整体重编码"，这正好踩在最痛的地方。

Fast Cut 的默认答案更干脆：**吸附关键帧、整段流拷贝**——切点前移到最近的关键帧，画面数据
一个字节都不动。这就是"不掉画质"的最强形式，代价是切点会多带一小段开头。

需要切点逐帧精确时（导出面板勾选「精确模式」），走的是第二条路：**能拷就拷，只在不得不编的地方编**。

```
[ 重编码入点那一小段 ][============ 其余全部流拷贝 ============]
   有损，但只有这一小段        零转码、零画质损失
```

原因是流拷贝（`-c copy`）有个硬约束：**切点必须落在关键帧上**。想从任意一秒开始剪，就只能在
入点那一小段重编码。于是（精确模式下）：

- 入点**正好**落在关键帧上 → 整段流拷贝，**一个字节都不动**；
- 入点落在 GOP 中间 → 只把 `[入点, 下一个关键帧)` 这一小段重编码（CRF 18、同 profile），其余照旧流拷贝。

代价被明确摊开：那一小段是有损的。但**换来的是剪辑位置精确、以及整段素材画质不被破坏**——
而且这一切在界面上是**可见**的：每段都标出它是纯拷贝、只重编了入点、还是整段重编码。

**顺带一条：不重编码就等于快。** 流拷贝的耗时≈磁盘拷贝，这是"导出快"的根本来源，不是调优出来的。
实测同一份 30 分钟 720p 素材：流拷贝导出 **6.2 秒**，整段重编码外推要 **36.6 秒**（差 5.9 倍）。

## 3. 它能做什么

### 编辑：像普通剪辑软件一样，但只有粗剪需要的东西

时间轴上是若干**片段**，首尾相接；删掉一段，后面立刻并拢，总长实时变短。这正是主流剪辑软件的
手感，只是没有多余的东西。

| 动作 | 操作 |
|---|---|
| 播放 / 暂停 | `空格` |
| 变速试听 | `J` 减速 / `K` 暂停 / `L` 加速（0.25×–8×） |
| 逐帧 | `,` `.` |
| 跳关键帧 | `Shift+←` `Shift+→` |
| 跳分割点 | `Shift+↑` `Shift+↓` |
| **切分** | `W` 在播放头处分割 |
| **删前一段** | `Q` 删掉播放头到上一个分割点 |
| **删后一段** | `E` 删掉播放头到下一个分割点 |
| **删整段** | `Backspace` |
| 调整切点 | 拖片段之间的**分割线** |
| 合并片段 | **双击**分割线 |
| 改片段顺序 | 拖**胶片条**（数组顺序即导出顺序，乱序也能正确拼接） |
| 撤销 / 重做 | `Ctrl+Z` / `Ctrl+Y` |
| 缩放 / 适应 | `+` `-` / `Ctrl+0` |
| 导入 / 导出 | `Ctrl+O` / `Ctrl+E` |

- **全键盘**：界面上没有"分割/删除"按钮，剪辑动作全走键盘，手不用离开键位。
- **键位可改**：⌨ 面板里逐条改，存进 userData。
- **时间轴胶片条**按缩放动态抽帧，任何倍率下都不重叠、不放大。
- **顶部刻度条**兼作播放头手柄，带磁吸（优先吸分割点，其次 GOP 边界）；拖胶片不会移动播放头。

### 导出

- **拼接成一个文件**（默认）或**每段一个文件**（`name-01.ext`）；
- 容器默认跟随源，也可**只换封装**为 MP4 / M4V / MOV / MKV——编码一律不动；
- 导出前给出文件名、时长、大小预估和全部警告；有进度、可取消（不留半成品）；
- **绝不覆盖**：目标已存在、或目标就是源文件，直接拒绝。

### 画质：默认吸附整段零损失，精确模式只在不得不编的地方编

| 情况（吸附模式，默认） | 处理 | 画质 |
|---|---|---|
| 切点吸附到关键帧（自动） | 整段流拷贝 | **零损失**（逐帧哈希一致） |
| 吸附会吞掉已删的间隙（间隙 < GOP） | 该段自动改为局部精确 | 仅入点小段有损，预估写明 |

| 情况（精确模式，勾选后） | 处理 | 画质 |
|---|---|---|
| 入点正好在关键帧上 | 整段流拷贝 | **零损失** |
| 入点落在 GOP 中间 | 只重编码入点那一小段，其余流拷贝 | 仅入点小段有损 |
| 源编码没有同编码重编码器（MPEG-4 ASP / MJPEG / ProRes…） | 整段重编码 | 有损，界面明说"非流拷贝" |
| VFR（可变帧率）源 | 整段重编码为定帧率 | 有损，界面明说 |

**流拷贝段是真正的零损失**——实测把源与产物的帧逐一做 MD5 比对，**40/40 完全一致**。

### 自检：导出后自动逐项核对，任何一项不过就报错

容器、视频编码、分辨率、像素格式、帧率、profile、色彩特性、音轨数量、字幕轨数量、
**帧数符合切割计划**、时长符合预期、**音画时间线一致**、**解码无错误**。

**宁可失败，也不静默交出一个坏文件。** 这条是设计原则：所有"这次没走流拷贝"的情况都会在界面上写明，
不会让你在事后才发现画质被动了。

### 字幕

带 SRT/ASS 的源，字幕按**文本重新计时**（段里不带字幕，拼接时一次上轨），不会丢 cue、不会串位。
位图字幕（PGS/DVD）这类无法重排的，只要出现分段就会被自检拒绝并说明原因。

## 实测数据

在一台 i5-13600KF 机器上，用 **30 分钟 / 720p / 30fps / 1.18 GB** 的录制素材实测：

| 指标 | 实测 |
|---|---|
| 冷启动到窗口出现 | **256–618 ms**（装完首次启动约 1.2 s，杀软在扫新文件） |
| 探流（导入即可预览） | **39 ms** |
| 全片关键帧扫描 | **491 ms**（216 个关键帧；后台跑，不挡预览） |
| 编辑计划生成 | **1 ms**（纯内存，不碰磁盘） |
| 删除两段后导出（成片 1280 s / 838 MiB） | **6.2 s** |
| 空载内存 | 318 MiB |
| 流拷贝 vs 整段重编码 | 6.2 s vs 36.6 s（**快 5.9 倍**） |

**编辑本身是纯内存操作**：切分、删除、调切点、改顺序都只改内存里的片段数组，不产生任何磁盘 IO，
所以"编辑快"跟素材多大无关。只有点导出时才真正动 ffmpeg。

## 环境与构建

- Windows 10/11 x64，Node.js 20+
- `npm install`

### 构建 exe 前需要自备 ffmpeg

`vendor/ffmpeg/` 里要放 `ffmpeg.exe` 与 `ffprobe.exe`（该目录被 `.gitignore` 排除，不入库）。
electron-builder 会把它复制进 `resources/ffmpeg`，**打包版只用内置的这一份**，不提供用户覆盖入口。
安装包之所以有 133 MiB，主要就是这两个文件（未压缩 231 MiB）；**自写代码只占 0.26 MiB**。
注意：常见的公开构建是 GPL 编译的，自行分发 exe 时需一并履行相应义务。

### 命令

```bash
npm start              # 开发运行
npm run core:test      # 剪辑内核单元测试（72 个）
npm run smoke          # 端到端自检：开真窗口跑完整剪辑 + 导出 + 时间轴交互（79 项）
npm run core:codecs    # 编解码矩阵：12 条素材 × 2 种导出模式 × 换封装（30 格）
npm run dist           # 打包 → dist/Fast-Cut-Setup-<版本>-x64.exe（NSIS 安装向导）
npm run dist:dir       # 只出 dist/win-unpacked/，调打包配置时快得多
```

`core:codecs` 的判据不是"全部成功"，而是**不许静默交出差文件**：要么自检通过、且独立复核
（自己再解一遍码 + 逐报文算音视频真实时间线差 + 帧数对计划）也干净；要么自检失败并说清哪一项没过。

## 已知限制

- **未做代码签名**：下载与首次运行都会被 SmartScreen 拦一下，需要手动选择"仍要运行"。
- **只处理单文件**：不支持多源拼接（也从根上规避了参数不一致）。
- **吸附模式会多带开头**（默认模式）：切点前移到关键帧，产物比选区多带一段开头（预估里逐段写明带多少）。
  把切点对准 GOP 边界（跳关键帧键 `Shift+←/→` + 磁吸就是为此）即多带为零；要逐帧精确勾「精确模式」。
- **精确模式的入点小段是有损的**：那一小段（最长约一个 GOP）会被重编码（CRF 18、同 profile，实测 SSIM 0.998）。
- **源编码没有同编码重编码器时整段重编码**：MPEG-4 ASP / MJPEG / ProRes 等，导出编码会与源不同，
  界面与自检都会明说"非流拷贝"。
- **VFR 源整段重编码为定帧率**：帧长不均匀时"按帧数切"必然与音频对不上。
- **末端比选区少 2 帧（约 67 ms）**：只影响**结束在源中间**的片段（也就是你删掉一段之后留下的
  每个片段），每个少 `has_b_frames` 帧（H.264 录制素材通常为 2）——**选区最后 2 帧不出现在产物里**，
  片段比选区短 67 ms。**音画不失步**（实测音视频跨度差 0.02 s，远小于自检阈值 0.3 s），
  无黑帧、无花屏。结束在源尾的片段一点不少。这是刻意的取舍：
  **宁可切短 2 帧，也绝不把已删素材带回来**（实测按包数硬切会把出点外已删的帧带进来）。
- HEVC / AV1 的**预览**取决于机器上有没有对应解码器；解不了只影响预览，流拷贝导出不受影响。
- 内置 ffmpeg 为 GPL 构建，自行再分发这个安装包时需一并履行相应义务。

## 隐私

无遥测、无网络请求。全程只读源文件，导出只写你指定的目录；目标重名或就是源文件时直接拒绝，
**绝不覆盖用户的素材**。
