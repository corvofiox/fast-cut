# Fast Cut

一个只做裁剪的 Windows 桌面视频工具：**导入即播，框选即剪，导出不等**。

---

## 1. 这是一个什么项目

Fast Cut 是一个**极简的、只做裁剪**的视频工具。把一段视频导进来，框掉不要的片段，按源格式
原样导出去，就这些。

它不做时间线编辑、轨道叠加、转场、滤镜、调色、字幕烧录、变速、加水印——那些交给
Premiere / 剪映 / DaVinci。它也**不做格式转换**：导出不会把 H.264 变成 H.265，唯一允许的
"换格式"是**只换封装**（remux，MP4 / M4V / MOV / MKV），编码一个字节都不动。

技术上它是一个 Electron 桌面应用（Windows 10/11），内核是一层不依赖 Electron 的纯 Node
模块，所有实际剪辑动作都由内置的 ffmpeg 完成。**无遥测、无网络请求**，离线可用。

### 核心承诺：剪辑位置精确到帧

这是整个产品的立足点，也是它和同类工具最大的分歧：

> **你选哪一秒，就从哪一秒起。入点绝不吸附、绝不回溯到关键帧，你剪掉的素材一秒都不会回到产物里。**

## 2. 为什么要有这个项目

**因为"无损裁剪"这件事，现有工具的取舍让人难受。**

视频压缩的基本事实是：只有**关键帧**（I 帧）能独立起播，中间那些帧依赖前后的帧才能解出来。
所以传统的"无损裁剪"（`ffmpeg -c copy`）有一个硬约束：**切点必须落在关键帧上**。

这带来一个用户能直接感受到的后果。假设关键帧每 8 秒一个，你想从第 3 秒开始剪——工具只有两条路：

| 做法 | 结果 | 代价 |
|---|---|---|
| **往前找关键帧**（绝大多数工具的做法） | 从第 0 秒开始 | 你要删掉的 3 秒**又回来了** |
| 往后找关键帧 | 从第 8 秒开始 | 你要保留的 5 秒**被删掉了** |

于是"无损"和"精确"变成了一道二选一。**Fast Cut 拒绝做这道选择题**，它给的答案是第三条路：

```
[ 重编码入点那一小段 ][======== 其余全部流拷贝 ========]
  有损，但只有一小段        零转码、零画质损失
```

- 入点**正好**落在关键帧上 → 整段流拷贝，完全无损；
- 入点落在 GOP 中间 → **只把 `[入点, 下一个关键帧)` 这一小段重编码**（CRF 18、同 profile），
  其余照旧流拷贝。

代价被诚实地摊开：那一小段是**有损**的。但换来的是**剪辑位置永远准**——而且这个代价是
可见、可解释、可预期的，不是"你的开头莫名其妙多了 3 秒"。

**另外两件必须解决的事：**

**① 快。** 流拷贝的耗时≈磁盘拷贝，10 分钟 1080p 源裁一段实测 **449 ms**。一旦退化成
整段重编码，同样的事情要几分钟到十几分钟——产品卖点直接归零。所以"快"在这个项目里是
功能设计的一部分，不是性能调优项。

**② 字幕不能悄悄错位。** ffmpeg 逐段定位 Matroska/MP4 的字幕轨是不可靠的（实测会整条漏掉
落在切割窗口里的字幕，也会把已删区间的字幕串回来，而且"漏一条 + 串一条"会让条数刚好相等，
骗过条数校验）。所以 Fast Cut 不靠 ffmpeg 切字幕：**段里不带字幕**，改成把 SRT/ASS 抽成文本、
按保留区间映射到成片时刻、在拼接那一步一次性上轨。位图字幕（PGS/DVD）和 mov_text 不是能重排的
文本字幕，这种源只要出现分段就会被自检拒绝并说明原因——**绝不静默交出一个字幕错位的文件**。

**贯穿始终的一条原则：宁可失败，也不静默出错。** 导出后必须逐项自检（见下），任何一项不符
就报错、不交半成品；所有"这次没走流拷贝"的情况都在界面上写明。

## 3. 它能做什么

### 剪辑

| 能力 | 说明 |
|---|---|
| 导入 | 文件选择 / 拖拽进窗口 / 拖到 exe 图标 / `Ctrl+O`；`mp4 mov m4v mkv avi webm flv ts mts` |
| 预览 | 原生 `<video>` 直读源文件（硬件解码），**不转码、不做代理、不额外占磁盘**；跨接缝自动接下一段 |
| 粗剪 | 全键盘：`W` 分割、`Q`/`E` 涟漪删除、`Backspace` 删整段、`Ctrl+Z`/`Ctrl+Y` 撤销重做 |
| 试听 | `J`/`K`/`L` 变速（0.25×–8×）、`,` `.` 逐帧、`Shift+←/→` 跳关键帧 |
| 时间轴 | 刻度尺兼播放头手柄 + 胶片缩略图；拖动胶片可**改片段顺序**、单击选中，两者都不移动播放头 |
| 键位 | 界面上只有 ⌨ 一个入口，**所有剪辑动作都能改键位**，存进 userData |

时间轴刻度显示的是**成片时间**：删掉一段，后面的立刻并拢，总长实时变短，跟剪映 / Premiere 的手感一致。

### 导出

- **拼接成一个文件**（默认）或**每段一个文件**（`name-01.ext`）；
- 片段顺序就是你拖出来的顺序，**乱序也能正确拼接**；
- 容器默认跟随源，也可只换封装为 **MP4 / M4V / MOV / MKV**（不重编码）；
- 导出前给出文件名、时长、大小预估与所有警告；导出有可见进度，可随时取消（不留半成品）。

### 自检（导出后自动执行，任何一项不过就算失败）

容器、视频编码、分辨率、像素格式、帧率、profile、色彩原色/传输特性、音轨数量、字幕轨数量、
**帧数符合切割计划**、时长符合预期、**音画时间线一致**、**解码无错误**。

其中几条判据是踩坑踩出来的：帧数比时长更硬（容器记账口径会糊弄时长，帧数不会）；
音画时间线要逐报文算（容器总时长看不出"音频比视频长半秒"这类接缝病）。

### 边界（明确的、有意为之的限制）

- **只处理单文件**：不支持多源拼接（也从根上规避了参数不一致）；
- **不导出到与源不同的编码**：源编码没有同编码重编码器时（MPEG-4 ASP / MJPEG / ProRes 等），
  入点不在关键帧上就只能**整段重编码**，此时导出编码会与源不同——界面与自检都会明说"非流拷贝"；
- **VFR（可变帧率）源整段重编码为定帧率**：帧长不均匀时"按帧数切"必然与音频对不上；
- **B 帧源的末端可能少 1~2 帧**：流拷贝按解码序数包，做法是宁可末端"多停一下"，
  也绝不把你已经删掉的素材带回来；
- **不覆盖任何文件**：目标已存在、或目标就是源文件，直接拒绝；
- **不做**代码签名（首次运行 SmartScreen 会拦一下）、自动更新。

## 环境与构建

- Windows 10/11 x64，Node.js 20+
- `npm install`

### 构建 exe 前需要自备 ffmpeg

`vendor/ffmpeg/` 里要放 `ffmpeg.exe` 与 `ffprobe.exe`（该目录被 `.gitignore` 排除，不入库）。
electron-builder 会把它复制进 `resources/ffmpeg`，**打包版只用内置的这一份**，不提供用户覆盖入口。
注意：常见的公开构建是 GPL 编译的，自行分发 exe 时需一并履行相应义务。

### 命令

```bash
npm start              # 开发运行
npm run core:test      # 剪辑内核单元测试（72 个）
npm run smoke          # 端到端自检：开真窗口跑完整剪辑 + 导出 + 时间轴交互（79 项）
npm run core:codecs    # 编解码矩阵：12 条素材 × 2 种导出模式 × 换封装（30 格）
npm run dist           # 打包 → dist/Fast-Cut-Setup-<版本>-x64.exe（NSIS 安装向导）
npm run dist:dir       # 只出 dist/win-unpacked/，调打包配置时快得多
```

`core:codecs` 的判据不是"全部成功"，而是**不许静默交出差文件**：要么自检通过、且独立复核
（自己再解一遍码 + 逐报文算音视频真实时间线差 + 帧数对计划）也干净；要么自检失败并说清哪一项没过。

## 隐私

无遥测、无网络请求。全程只读源文件，导出只写你指定的目录；目标重名或就是源文件时直接拒绝，
**绝不覆盖用户的素材**。
